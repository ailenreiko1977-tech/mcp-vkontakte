# Проверка пользовательского доступа VK

Цель: проверить возможность вызова `groups.search` от имени пользователя для собственного VK-приложения. В схеме VK у этого метода указан только тип `user`; сервисный ключ текущего приложения на практике получил код 15 без уточняющего подкода. Наличие пользовательского поля в кабинете и получение любого VK ID токена сами по себе не подтверждают право на поиск.

## Проверка через VK Mini App

В проект добавлена страница `/vk-app`. Она включается только при явно заданном положительном `VK_MINI_APP_ID` в конфигурации сервера. В качестве адреса размещения мини-приложения нужно указать полный HTTPS URL этой страницы в собственном кабинете VK для разработчиков. Условия размещения и разрешения подтверждает владелец приложения; само размещение страницы не подтверждает доступ к API.

1. Открыть мини-приложение внутри VK под своим аккаунтом.
2. Нажать «Разрешить доступ и проверить поиск». Официальный VK Bridge запросит только scope `groups`.
3. После разрешения вызывается один `groups.search` по слову «нейрокино», count=3.
4. Если поиск отказал, страница показывает этап и числовой код ошибки. Ключ не предлагается к сохранению. Если доступ не выдаётся приложению, потребуется уточнить официальные условия VK; этот проект не обходит их.
5. Если поиск прошёл, пользователь может нажать «Скопировать проверенный ключ», затем добавить его в своём HTTPS-кабинете как `vk_user`, тип «Пользовательский токен API».
6. После этого отдельно проверить ключ запросом с VPS. Успех внутри VK не доказывает серверную совместимость; возможны ограничения приложения, срока и привязки токена.

## Секреты и границы безопасности

Страница использует локальную копию официального `@vkontakte/vk-bridge` 2.15.0, проверенную по SHA-512 npm-архива. Лицензия включена в `vk_mcp/web/VK_BRIDGE_LICENSE.txt`. Сценарии установки npm-пакета не запускались.

Полученный пользовательский ключ остаётся в замыкании JavaScript в памяти страницы. По умолчанию он не выводится в DOM, не логируется, не сохраняется в localStorage/sessionStorage и не отправляется на наш сервер. При отказе браузерного копирования используется официальный VKWebAppCopyText; если он тоже отказал, пользователь может отдельным нажатием показать ключ в readonly-поле для ручного Ctrl+C. Это поле очищается при новой проверке и уходе со страницы. Копирование происходит только по отдельному нажатию после успешной проверки поиска. Страница не запрашивает личные сообщения, фотографии, друзей или разрешения записи на стене.

Только публичная страница `/vk-app` разрешает встраивание доменами VK. Кабинет, OAuth-вход и подтверждения изменений сохраняют запрет встраивания. Для проверочной страницы запрещены HTML-формы и прямые сетевые соединения скриптов; общение с VK идёт через официальный Bridge и родительское окно VK. Серверного API для приёма токена этой страницей нет. Параметры запуска mini app не используются для авторизации в нашем кабинете или выбора пользователя.

## Результат проверки на VPS, 23 октября 2026

После разрешения владельца поиск `groups.search` успешно выполнен как внутри VK, так и непосредственно с VPS. Повторный запрос с VPS после остановки временного SSH-канала также успешен: по тестовому запросу «нейрокино» найдено 2 сообщества. Сохранённые подключения сообщества и сервисного ключа при этом не изменялись.

У первого ключа, полученного через обычное подключение браузера, серверный вызов завершился ошибкой 5, подкод 1130: `access_token was given to another ip address`. Новый ключ был получен владельцем вручную через временный канал с выходом через VPS. Это подтверждает работу конкретного проверенного ключа; переносимость на другой адрес не подтверждена.

Официальный `secure.checkToken` показал для проверенного ключа срок жизни 86400 секунд, то есть 24 часа. Автоматическое обновление не реализовано. В объявленном результате `VKWebAppGetAuthToken` есть `access_token`, `scope` и необязательные `expires`/`status`; `refresh_token` отсутствует. Текущий сервер хранит только ключ доступа и не может самостоятельно продлить его по механизму VK ID.

В официальном VK ID SDK есть отдельный механизм `refreshToken(refreshToken, deviceId)`. Его наличие не доказывает, что выдаваемый таким способом ключ позволит вызывать `groups.search`. Перед внедрением нужны отдельная авторизация, успешный поиск с VPS, обновление ключа и повторный успешный поиск обновлённым ключом. Действующие подключения для такого эксперимента заменять не следует.

Источники механизма обновления: [тип результата VK Bridge](https://github.com/VKCOM/vk-bridge/blob/master/packages/core/src/types/data.ts), [реализация авторизации и обновления VK ID](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts), [типы результата VK ID](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/types.ts).

## Отдельный тест VK ID

Оператор может включить `/vkid-test`, задав `VKID_TEST_APP_ID` (ID отдельного Web-приложения VK ID) и `VKID_TEST_OWNER` (внутренний owner principal учётной записи оператора). По умолчанию маршруты выключены. Доверенный redirect URL приложения должен точно совпадать с `PUBLIC_URL/vkid-test/callback`.

Начало теста требует входа владельца в кабинет, POST с проверкой Origin и CSRF. Authorization Code с PKCE S256 привязан к текущей серверной сессии, одноразовому state и сроку 10 минут. После ручного входа пользователя сервер обменивает код, вызывает `groups.search`, пробует refresh и повторяет поиск. Ошибки выводятся только как коды, без исходных ответов провайдера. Access/refresh tokens и device_id не записываются в БД или логи, не выводятся в браузере; они используются только в обработчике проверки. В памяти на 10 минут остаётся результат без ключей, а незавершённые попытки удаляются при следующем обращении после истечения срока. Перезапуск сервера сбрасывает попытки и результаты.

Тест не сохраняет новое подключение и не обновляет существующие. Даже успех всех этапов показывает только работоспособность текущего разрешения и немедленного обновления; фоновое обновление после истечения access token требует отдельной реализации и проверки. Отсутствие scope `groups` в кабинете VK ID не следует маскировать: отказ авторизации или поиска является результатом теста.

Первичные источники: [VK Mini Apps API: запрос пользовательского ключа](https://github.com/VKCOM/vk-mini-apps-api/blob/master/src/index.ts), [VK Bridge](https://github.com/VKCOM/vk-bridge), [схема groups.search](https://github.com/VKCOM/vk-api-schema/blob/master/groups/methods.json).
